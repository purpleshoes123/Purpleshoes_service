# 운영 배포·장애 대응 매뉴얼

## 정상 배포

1. 작업 브랜치의 PR 검증을 통과시킵니다.
2. 리뷰 후 main에 merge합니다. 직접 push도 동일한 배포를 시작합니다.
3. Actions verify·deploy 결과와 실제 영향 영역을 확인합니다.
4. 커밋·실행 링크·테스트·남은 한계를 기록합니다.

운영 작업은 직렬 실행하며 다음 push 때문에 진행 중 작업을 강제 취소하지 않습니다. 마지막 배포 기준과 현재 커밋을 비교해 변경 영역을 결정합니다.

| 영역        | 진행                                                       | 완료 판단                              |
| ----------- | ---------------------------------------------------------- | -------------------------------------- |
| 서버        | Linux 패키지·해시 → 비공개 S3 → 시작 설정 복제 → 순차 교체 | 전체 새 서버·ALB 정상, 로컬·공개 ready |
| 메일        | 새 서버 확인 후 영속 활성 게이트 전환                      | 실제 작업자 자식 프로세스              |
| 테마        | 전체 복구 폴더 백업 → 변경 파일 충돌 검사 → 선택 반영      | Shopify 재다운로드 내용·해시 일치      |
| 대용량 자산 | 5MiB 초과 파일을 암호화 S3·5분 링크로 전달                 | 비동기 처리 완료·원본 해시 일치        |
| 앱 확장     | 설정·기존 확장 확인, 이전 활성 버전 기록 후 변경 배포      | 릴리스와 영향 기능 확인                |

Shopify CLI는 5분 시간 제한이 있습니다. 서버 교체는 안정화·연결 정리로 수십 분 걸릴 수 있습니다. 진행률만 보고 서버를 임의로 중단하지 않습니다.

배포 러너에도 Shopify 확장 잠금 파일로 의존성을 설치합니다. 검증 러너와 파일 시스템은 공유되지 않습니다. 앱 설정과 이전 활성 버전은 서버 교체 전에 확인해, 설정 오류 때문에 서버를 교체했다가 복구하는 시간을 줄입니다. 앱 배포·복구는 CLI 5의 `--allow-updates --no-input`을 사용하며 확장 삭제는 허용하지 않습니다.

ASG 최대 용량이 현재 운영 수의 두 배 이상이면 최대 정상 용량 200%로 새 서버를 함께 준비합니다(평소 2대·최대 4대이면 교체 중 최대 4대). 여유가 작으면 기존 150% 방식을 유지합니다. 최소 정상 용량 100%, 서버 안정화 300초, 로드밸런서·메일 작업자 검사와 자동 복구는 유지합니다.

## 오류별 확인

### PR 실패

실패한 첫 단계를 읽습니다. 포맷 오류는 format 명령으로 수정하고 테스트 실패는 환경 문제·경로 오류·동작 변화를 구분합니다. DB·테마 설정·삭제 보호에 걸리면 별도 작업 계획을 검토합니다. 검사를 끄지 않습니다.

### 배포 전 테마 충돌

운영 편집기나 외부 도구에서 파일이 바뀌었을 수 있습니다. 실제 파일과 Git을 비교해 의도한 변경을 정리합니다. 현재 커밋으로 기준을 덮어써 충돌을 숨기지 않습니다.

### 새 서버 비정상

ASG 교체·숫자 시작 버전·ALB 대상, app·nginx·로컬 ready, 패키지 읽기 권한을 확인합니다. DB·Valkey는 보안 저장소·인증서·네트워크·역할을 확인하며 비밀값을 로그에 출력하지 않습니다. 기존 정상 용량을 보존합니다.

### 구매 메일 미수신

메일 활성 설정·전환 시각·스토어·상품 조건, 영속 대기열·중복 방지·반송·수신 거부·제공자 결과를 확인합니다. 활성 게이트와 실제 작업자를 확인합니다. 과거 주문 전체를 재처리하거나 이전 마케팅 Flow를 무작정 켜지 않습니다.

### 관리자·고객 정보 불일치

동일 고객·주문·예약을 보는지 확인한 뒤 검증된 요청·영속 기록·Shopify 메타필드·임시 캐시의 역할을 구분합니다. 캐시 삭제나 DB 직접 수정부터 시작하지 않습니다.

## 복구

일반 실패 시 도구는 이전 숫자 시작 설정으로 순차 복구하고 메일 게이트를 되돌립니다. 테마는 백업 파일 복원·대조, 앱은 이전 활성 버전 복구를 시도합니다. 미완료 표시가 있으면 직접 확인해야 합니다. 참조되지 않는 새 테마 자산은 남을 수 있습니다.

**실행 취소·러너 강제 종료·시간 초과는 정상 예외 처리와 다를 수 있습니다.** 취소 후 복구 완료로 가정하지 않습니다.

1. 이전 Actions와 AWS 교체가 실제로 끝났는지 확인합니다.
2. 서버 버전·상태·패키지 해시·메일 게이트를 확인합니다.
3. live 테마와 백업을 대조합니다. 복구 업로드 폴더에는 config·layout·templates가 필요합니다.
4. 필요한 서버·테마·앱 복구 후 다시 확인합니다.
5. 이전 상태를 백업하고 **실제 확인한 영역만** 비공개 S3 기준에 반영합니다.

서버만 확인됐고 테마가 미완료라면 전체 성공 기준으로 갱신하지 않습니다. 최초 연결 때 이 상태를 분리해 복구한 이력이 있습니다.

Git revert만으로 모든 복구가 끝나지는 않습니다. 테마 삭제·DB 변경 보호에 걸릴 수 있고 메일 활성 버전도 확인해야 합니다. 운영 주문·가격·권한·쿠폰 데이터는 코드 복구만으로 되돌아가지 않습니다.
